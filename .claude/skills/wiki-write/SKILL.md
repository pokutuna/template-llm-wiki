# wiki の書き方

wiki の構成と読み方は `.claude/rules/wiki.md` にある。まだ読んでいなければ先に読む。

## 共通の手順

1. `wiki/index.md` を読み、書く内容に近い既存ページを `list-pages.sh` と `rg` で探す
2. 既存ページのテーマに収まるなら、そのページに追記する。どのテーマにも収まらないときだけ新しいページを作る
3. 書いた内容によって古くなる記述が他のページにあれば、それも更新する
4. 書き終えたら「書いた後の確認」で変更したページを点検する

wiki への書き込みは 1 つのエージェントが順に行う。サブエージェントに並列で書かせない。
複数のエージェントが同時に書くと、同じページへの追記や他ページの更新が食い違う。

## 置き場所の判断

迷ったら、次の順で分類する:

1. 従うルール・規約か → `references/`
2. 外部資料に何が書いてあるかの記録か → `sources/`
3. 読んだ資料をもとに、あるテーマについて分かったことか → `research/`
4. 経験から得た理解・因果・教訓を、今後参照できる形で残すか → `findings/`
5. 特定の作業・調査・障害を、wiki に時点記録として残すか → `notes/`
6. これからやりたいことか → `ideas/`

- `sources/` は資料ごとに、その資料に書いてあることを記録し、解釈を加えない。
  `research/` はテーマごとに、複数の資料をまたいで分かったことと、その解釈を書く
- `notes/` は経緯・観測、`findings/` はそこから得た理解・教訓を記録する。同じ出来事から両方作ってよい。
  `findings/` の元は `notes/` に限らず、作業の成果物、`research/`、外部資料など何でもよい
- 人が読む設計書・レポート・発表資料は `wiki/` ではなく `docs/` に置く

## 外部資料を取り込む

URL や資料を渡されて wiki への取り込みを頼まれたときの手順。資料の本文はコピーしない。
どこに何が書いてあるかを `sources/` に残し、分かったことを他のページに反映する。

1. 資料の単位を決める。単位は人が名前で呼ぶまとまり (ドキュメントサイト、リポジトリ、仕様書、論文、記事、動画) とし、
   同じサイトの別のページは同じ Source ページにまとめる
2. その資料の Source ページが既にあるか探す: `rg '^resource: <資料のルート URL>' wiki/sources`
3. 資料を実際に読む。読めないときは推測で書かず、ユーザーに本文を貼ってもらう
4. Source ページを作る、または既存のページに追記する (書式は次節)。実際に読んだページだけを `sources` に足す
5. 既存の wiki と照らし合わせて、資料から分かったことの扱いを決める
   - 新しい知識がある → `research/` などの該当ページに追記するか、新しいページを作る
   - 既存の記述と食い違う → 古い記述を残したまま更新の印を付ける (「古くなった記述」)
   - 新しい知識が無い → Source ページへの記録だけで終える
6. 他のページから資料を出典として参照するときは、`sources[].resource` に Source ページ (`../sources/<slug>.md`) と
   資料の URL のどちらを書いてもよい

数値、日付、バージョン、引用は、資料の中で該当箇所を見つけてから書き、資料の表記のまま写す
(資料が `42K` なら `42,000` と書き換えない)。資料の中に見つからない値は書かない。

### Source ページの書式

- ファイル名は資料名の小文字ケバブ (例: `example-docs.md`)
- `resource` に資料のルート URL、`sources` に実際に読んだページを書く (どちらも必須)
- 抜粋は資料の文をそのまま短く引用し、どのページの文かが分かる位置 (そのページの見出しの下) に置く
- 1 つの資料のページが 300 行を超えたら、資料のセクション単位に分ける (例: `example-docs-api.md`)

```markdown
---
type: Source
title: Example ドキュメント
description: Example の公式ドキュメント。設定項目、プラグインの作り方、移行ガイドがある。API リファレンスは無い
tags: [example]
generated: { by: claude-code/claude-opus-5-5, at: 2026-10-18T15:00:00+09:00 }
resource: https://docs.example.com/
sources:
  - resource: https://docs.example.com/config/
    title: Configuration
---

# Example ドキュメント

## 概要

<!-- 発行者、対象のバージョン、公式かどうか、資料全体の構成 -->

## ページ

### [Configuration](https://docs.example.com/config/)

- 読んだ日: 2026-10-18
- 内容: <!-- このページで扱っている話題の列挙 -->
- 要約: <!-- 2〜3 文 -->
- 抜粋:
  > <!-- 資料の文をそのまま引用する -->

## 無いもの

<!-- 探したが見つからなかった情報。同じ探し物を繰り返さないために書く -->
```

## 新しいページを作る

1. `cp wiki/template.md wiki/<dir>/<slug>.md` — slug は小文字ケバブ (例: `sprite-pipeline.md`)
   - `notes/` は `yyyymmdd-<slug>.md` 形式 (例: `20261018-initial-setup.md`)、その他は日付なし
   - note の日付は、記録を始めた日または最初に重要な結果を得た日とする
2. frontmatter を埋める (下記規約)。`type: Template` は必ずディレクトリに対応する値に書き換える
3. 関連する既存ページの「関連」節から、新しいページへリンクする
4. 全作業の前提になるような特に重要なページなら、`wiki/index.md` の「重要」セクションに載せる (通常は不要)

## ページの育て方

- `research/`、`findings/`、`sources/` は追記して育てる。追記時は既存の見出し構成に沿い、`generated` を更新する
- `notes/` は必要な場合だけ作る。作業中は追記し、完了後は原則固定する
- `research/` は実際に読んだ資料に基づいて書き、会話や一般論で内容を補わない
- ページが 300 行を超えたら、テーマを分けて別ページにする。元のページには分けた先へのリンクを残す

### 古くなった記述

新しい結果や資料が既存の記述と異なるときは、古い記述を消さず、その直後に更新の印を書く。
条件の違いや変わった理由が分かるなら、それも書く。

```markdown
> [!NOTE]
> 2026-10-18 更新: v2 からデフォルトで有効になった。[Example ドキュメント](../sources/example-docs.md)
```

ページ全体が現行でなくなったときは、ページを消さずに `status: deprecated` を付け、冒頭に後継ページへのリンクを書く。

## アイデアから記録までの流れ

1. アイデアを `wiki/ideas/<slug>.md` に書く
2. 試した結果、wiki に残す価値があれば、経緯は `notes/yyyymmdd-<slug>.md`、発見は `findings/` に記録する。
   必要に応じて `research/` や `references/` にも整理する。wiki の記録は必須ではない
3. 元の idea ページの `progress` を更新する

## frontmatter 規約

| フィールド | 扱い | 内容 |
| --- | --- | --- |
| `type` | 必須 | `Reference` / `Source` / `Research` / `Finding` / `Note` / `Idea` (ディレクトリ対応表のとおり) |
| `title` | 必須 | ページタイトル |
| `description` | 必須 | 1 文の要約。ページを開かず内容を判断するために使う |
| `tags` | 推奨 | 小文字ケバブの配列 |
| `generated` | 推奨 | `{ by: <actor>, at: <日時> }`。最後に実質的な内容変更をした主体と日時。作成時に設定し、内容を更新したら書き換える |
| `resource` | `sources/` では必須。他は任意 | このページが説明する対象。外部なら URL、リポジトリ内ならこのページからの相対パス |
| `sources` | `references/` `sources/` `research/` では必須。`findings/` では推奨 | 実際に読んだ出典のリスト (下記) |
| `verified` | 任意 | `{ by: human:<id>, at: <日時> }`。人が内容を確認したときだけ付ける |
| `status` | 任意 | `deprecated` のみ使う。現行でなくなったページに付ける (無ければ現行) |
| `progress` | `Idea` では必須 | `open` / `doing` / `done` / `dropped` |

- 日時は ISO 8601 でオフセット付き (例: `2026-10-18T15:00:00+09:00`)
- actor は、エージェントなら `<ツール名>/<モデル名>` (例: `claude-code/claude-opus-5-5`)、人なら `human:<id>`
- エージェントは人の確認を経ずに `verified` を付けない
- 新しいタグを作る前に既存の使用例を確認し (`rg '^tags:' wiki/`)、表記ゆれを作らない

`sources` の各要素は `resource` (URL またはこのページからの相対パス) を必ず持ち、`title` を添える。
未読の URL や検索結果の一覧は載せない。

```yaml
sources:
  - resource: ../sources/example-docs.md
    title: Example ドキュメント
  - id: impl
    resource: ../../src/foo.ts
    title: foo の実装
```

本文で個別の主張に出典を付けるときは、`sources` の要素に `id` を付け、その id を脚注ラベルにする。

```markdown
foo は起動時に設定を 1 回だけ読む。[^impl]

[^impl]: foo の実装
```

## 本文の規約

- 外部情報に基づく主張には出典を添える (`sources` と脚注、または本文中の URL)
- `research/` では、資料に書かれている事実と自分の推測・解釈を分け、後者は明記する
- `findings/` には、可能な範囲で根拠となる成果物・note へのリンクを添える
- 未確認の仮説は断定せず、未確認であることを明記する
- wiki/ 内の他ページへは**相対リンク** (例: `../references/foo.md`)
- リポジトリ内のファイルへの言及はリポジトリルートからのパス (例: `src/foo.ts`)
- リンク先ページが未執筆でもリンクしてよい (書くべき知識のマーカーになる)
- 見出しと箇条書き中心で簡潔に。英数字・記号は半角

## 書いた後の確認

- `type` がディレクトリに対応していて、`type: Template` が残っていない
- 必須フィールド (`title`、`description`、ディレクトリごとに必須の `resource`・`sources`・`progress`) がある
- 追加したリンクの先が存在する (未執筆のページへの意図したリンクを除く)
- 新しいページに、他のページからのリンクがある
- タグが既存の表記と揃っている
- ページが 300 行を超えていない

## やらないこと

- `log.md` は作らない。wiki に残す作業ログは `notes/yyyymmdd-<slug>.md` に置く
- `wiki/` 直下に新規ページを増やさない (`index.md`, `template.md` のみ)
- 各ディレクトリに `index.md` を作らない。一覧は `list-pages.sh` で取る
- `wiki/` に frontmatter の無い `.md` ファイルを置かない (OKF の適合条件)
- 外部資料の本文を wiki にコピーしない。`sources/` には要約と短い抜粋だけを書く
- 重要度をファイルの場所で表現しない。重要なページは `index.md` の「重要」セクションに載せる。ファイルの移動はリンク切れの元
